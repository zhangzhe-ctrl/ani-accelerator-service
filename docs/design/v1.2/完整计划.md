# ANI GPU 资源管理服务详细计划 v1.2

**日期：2026-09-23｜建议服务：ani-accelerator｜基线：本次上传的 ani-governance.zip + v1.1 设计 + 后续明确讨论。**

本版是待实施的设计，不修改用户业务仓库，不宣称真实 GPU 接入通过。文件内标记“源码事实”指本次上传包或指明版本的官方源码；“本版决定”指新增设计。所引路径及行号、输入 SHA256、验证范围见附件。旧计划的“尚未实现”不能覆盖新上传源码中已经存在的实现；已有历史验收文件也不等于本次重新执行。

## 1. 结论、边界与变化

### 1.1 gpu-memory-factor 影响单位合同，不推翻架构

**它不是可以忽略的展示倍率。**本次读取的 `volcano-vgpu-device-plugin/v1.12.0` 源码中，Node 显存资源和节点设备注解均按 factor 缩小；Volcano 按请求中的同类数值调度；插件将分配数值乘回 factor 后设置容器显存限制。[W1–W4]

因此旧版“6 GiB 固定写 `volcano.sh/vgpu-memory=6144`”只对 factor=1 的这条适配路径成立。factor=1024 时应写6，而 Governance 仍占6144 MiB。**新版明确区分平台MiB、provider显存块、物理bytes和实时监控bytes。**

架构仍然是：配额在Governance，资源执行在Inference，供给和实际绑定在GPU服务。没有额外库存扣减，没有TCC确认阶段，没有RegisterConsumer强前置。

### 1.2 首期范围

同一集群静态整卡节点组与静态共享节点组；同节点同型号，供给组内节点匹配规格；每集群一种固定共享资源向量，另有整卡规格。共享是主功能，与整卡一起验证。每Pod一个GPU容器、每容器一张设备，业务可有多个固定副本；实际副本上限服从Inference已验证能力。

保留Inference既有控制器和正常重启；请求规格、副本数与factor基线在业务开放后冻结。没有在线模式切换、动态扩缩、额外滚动GPU副本、精确预留、独立Agent平台、自动排空或通用工作流。需要修改GPU实例镜像/模型而触发额外副本时，首期不默认开放该更新入口。

“预留”仅在末章记录扩展位置，不提供其Proto/数据表，也不将配额上限展示成已经预留。后续统一称“首期”，不把范围标签当成新组件。

### 1.3 对v1.1的明确替换

| v1.1事项 | v1.2决定 |
|---|---|
| Inference先RegisterConsumer再创建 | 删除强前置；Gov异步同步GPU使用关联 |
| 注册返回consumer_id才能打标签 | 直接使用Gov持久resource_id/create_operation_id；不另造必需Consumer ID |
| MarkConsumerClosing/FinalizeConsumer | 从首期执行链删除；关联只接收声明/结束投影 |
| ObserveRelease依赖Consumer/generation | 按可信资源引用+完整实际Pod范围核对；关联缺失不阻塞查询 |
| 固定vgpu-memory=MiB | 改为MiB/factor的整数块数，并冻结换算基线 |
| stable replica/allocation ordinal强制 | 删除首期强制；使用实际Pod UID+容器+父卡 |
| 管理员GetCapacity使用必填租户上下文 | 独立AdminGetCapacity，明确平台权限 |
| 其他设备证据冲突传播 | 先按设备归并，冲突局部化，汇总PARTIAL |

## 3. gpu-memory-factor：完整单位闭环

### 3.1 上游源码事实与适用边界

本次核对的发布路径为插件`v1.12.0`及Volcano`v1.12.0`对应源码，并对照公开问题记录。**这不等于用户当前部署版本，也不保证其他tag或分支相同。**正式接入必须锁镜像digest、代码修订、命令参数、配置摘要和实际有效值。

- 插件`apiDevices()`：每张卡生成`floor(floor(total_bytes/2^20)/F)`个显存设备条目。[W1]
- 插件`ConvertDeviceInfo()`：节点注册注解的`Devmem`同样除F。[W2]
- Volcano读取请求内的memory整数与节点Devmem比较；它不会替平台把“6144MiB”自动换成6块。[W3]
- 插件Allocate在HAMi软件路径设置`CUDA_DEVICE_MEMORY_LIMIT_i = Usedmem × F`，再加`m`后缀。[W1]

公开问题#85报告过多卡、大显存时ListAndWatch消息过大、Node显存上报为0，并建议提高factor。[W5] 不把某份FAQ的“32767”写成所有Kubernetes扩展资源的通用上限；本问题应按真实版本的设备条目/消息大小和错误日志定位。

### 3.2 平台字段与单位

| 名称 | 单位 | 用途 |
|---|---|---|
| `physical_memory_bytes` | bytes | NVML真实物理容量，不从缩小上报反推精确值 |
| `memory_block_mib`（F） | MiB/块 | 该冻结部署中一份provider显存单位代表多少MiB |
| `provider_memory_blocks` | 块 | Node注解/资源上报原值；不是张数、不是MiB |
| `reported_memory_mib` | MiB | `provider_memory_blocks × F`，量化后的可表达容量 |
| `safe_memory_budget_mib` | MiB | 经验证且不高于上报/物理容量的预算 |
| `shared_memory_mib`（m） | MiB/逻辑GPU | 产品规格与Gov计额依据 |
| `memory_blocks_per_device`（q） | 块/设备 | 渲染到vgpu-memory和归一化设备承诺的数值 |
| `runtime_limit_bytes` | bytes | 真实运行时验证/指标；不得再次乘F |

F不等于`deviceMemoryScaling`。前者改变表示粒度；后者涉及超配比例。首期memory/core scaling均为1，不通过factor增加物理容量。[W4]

### 3.3 精确换算：首期不静默取整

```text
q = m / F，要求F > 0、m > 0、m % F == 0
实际设置的显存MiB = q × F = m
本次共享占额MiB = replicas × devices_per_replica × m
```

首期拒绝无法精确表达的规格，错误`MEMORY_GRANULARITY_MISMATCH`；校验发生在发布/解析阶段、占额之前。后续可在“发布规格”时显式向上量化，必须显示实际规格并按实际量计额；不能创建时偷偷向下取整，或者界面6GiB而实际给5.996GiB。

| F | 产品规格m | vgpu-memory q | Gov单设备占额 | 处理 |
|---:|---:|---:|---:|---|
| 1 | 6144 | 6144 | 6144 | 精确 |
| 256 | 6144 | 24 | 6144 | 精确 |
| 1024 | 6144 | 6 | 6144 | 精确 |
| 10 | 6144 | 无精确整数 | 不占额 | 拒绝发布该组合 |

F=10时`614`对应6140MiB、`615`对应6150MiB；这两个都不是6144MiB。不能称factor只是展示倍率。另一个纯算术示例：`12285MiB/10`向下取整为1228块，实际只表达12280MiB；不推定用户实际factor或设备容量。

### 3.4 上报总量是逐卡取整再汇总

```text
T_d = floor(physical_memory_bytes_d / 2^20)
R_d = floor(T_d / F)
node_reported_blocks = sum(R_d)
node_quantized_mib = sum(R_d × F)
```

不要用`floor(sum(T_d)/F)`代替`sum(floor(T_d/F))`；逐卡余数不能跨设备组成一块。Node.status.allocatable是可用于分配的容量口径，不是已减去所有Pod申请后的实时free。

例如一张49140MiB设备，F=256：上报191块，对应48896MiB，244MiB是量化尾差；物理容量仍49140MiB。其他设备不能借用这244MiB来凑一个完整块。

平台读取多个来源时先标注来源单位：节点注解和调度分配Usedmem按块×F；NVML/bytes指标除2^20仅做展示；已归一化MiB不再次乘F。

### 3.5 整卡路径与尾差

整卡组仍使用number=1、cores=100、memory-percentage=100（需实际版本验证），不同时发送绝对memory。百分比100无需除F，但底层按量化后的父设备显存预算分配，再乘F，因此也可能留下不足F的尾差。

产品“整卡”表示该设备不与其他消费者共享，并不授权平台掩盖量化后可用显存。详情展示物理容量与验证后的可用容量。若业务要求不接受该尾差，应在业务开放前选择更小且可上报的F，或单独验证不重叠整卡节点组的固定配置；不动态改变运行中的F。

### 3.6 factor选择与配置检查

建议首期同一供给组所有节点使用相同F；能统一全GPU节点时更简单，但不把F写成不可扩展的全平台常量。不同F节点不得混入同一可替换组，否则同一Pod数值可能产生不同限制。

初装需要核对进程实际args和已加载配置，不只读ConfigMap期望值。本次源码有CLI与ConfigMap覆盖处理，其他版本可能不同；显式固定有效参数，禁止F=0。[W6]

选择F时同时满足固定规格整除、上报规模可接受、量化尾差可接受；1024只作为示例，不是对所有集群的部署建议。`memory_block_mib`进入baseline摘要和ResolvedGpuPlan，历史请求永不按最新F重算。观测报告还携带来源F/baseline，不能将旧样本乘新F。

配置未知或单组F不一致：停止发布/新解析，标记`CONFIG_DRIFT`或`MEMORY_UNIT_UNVERIFIED`；不是普通容量不足排队。已有Pending不因数据库CLOSED自动被底层隔离，必须按实际运维流程处理，不能宣称已有设备禁入能力。

## 4. 服务边界与两条流程

### 4.1 职责

| 服务 | 负责 | 不负责 |
|---|---|---|
| Governance | 套餐/额度/一次占额、业务命令可靠投递、原charge退额、GPU使用关联可靠同步 | 父卡选择、Pod删除、GPU运行状态权威 |
| Inference | 业务校验、持久接受、模型/镜像/工作负载、真实推理、关闭和清理、释放事实 | GPU公共供给配置、另一份配额账本 |
| GPU服务 | 静态组/规格/单位适配、设备清单、真实绑定和容量读模型、GPU使用关联投影 | 先抢库存、创建推理工作负载、决定Gov退款 |
| Volcano/插件/HAMi | 已验证的调度、分配和限制 | 套餐与平台用户权益 |

### 4.2 主流程与旁路

```text
创建主链：
用户 → Gov(认证/规格解析/一次占额+持久命令) → Inference(持久接受)
                                              → K8s/Volcano/HAMi → 模型加载/真实推理

关联旁路：
Gov从已提交原操作与charge派生“声明/结束” → SyncGpuUsage → GPU查询读模型

删除主链：
用户/受权管理员 → Gov(持久DELETE) → Inference(封闭创建+完整清理)
                               ← ReportQuotaRelease ← 删除完成事实
Gov幂等退额；旁路随后同步关联结束。
```

使用关联不是新的资源权利，不需要Confirm/Cancel三阶段。GPU服务不可用会影响新请求的必要规格解析；已经拿到冻结计划、完成Gov受理的请求，不再因为关联同步延迟而阻塞执行。清理需要的真实证据缺失可以阻塞退款，这是执行事实未知，不是Consumer行缺失。

### 4.3 简化身份

不强制另造Consumer ID。`GpuUsageRef`为`tenant_id + owner_service + resource_id + create_operation_id`。Gov生成稳定resource/operation，资源租户使用已有持久UUID映射；Gov内部tenant主键仍uint32。

Pod标签至少包含resource-id、create-operation-id、owner-service、resource-tenant-id，均由受权owner从已接受命令注入；完整摘要用annotation，避免64位hex超过label值63字符。规格范围通过受管supply-group/model-key/baseline-id标签约束。

不强制replica ordinal；实际绑定身份为`cluster_id + pod_uid + container_name + physical_device_id`。同一Pod多个来源去重，不同Pod UID不合并。平台资源ID不是物理GPU UUID。

## 5. 字段级对象与接口原则

完整字段/tag、类型、必填和范围见本包Proto及字段字典；BFF字段与新配置键见`运行配置与产品接线.md`。以下业务不变量与字段注释共同构成合同。源域RPC仅内部gRPC，无HTTP注解；Gov BFF单独映射，不增加跨服务HTTP。

### 5.1 核心对象

- `Cluster/Pool/SupplyGroup`：静态配置，不包含可手改的“剩余库存余额”。组内节点唯一归属；Node UID变化不得自动继承旧资格。
- `ProviderBaseline`：实际组件标识/digest、F、单位语义、共享上限、配置证据；证据不足不能自报VERIFIED。
- `GpuProfile`：不可变规格版本；共享绝对MiB、计算比例、适用组、provider块数与recipe。
- `ResolvedGpuPlan`：冻结GpuRequest、profile、runtime片段、MiB总量和F；摘要排除时间、观察状态和未来Pod身份。
- `GpuUsageProjection`：Gov申请在GPU域中的读投影，只有DECLARED/ENDED，不复制Inference Running/Failed。
- `GpuBinding`：实际分配或待确认事实；可先于关联投影存在；ACTIVE/RELEASE_CONFIRMED/UNKNOWN与业务状态分开。

### 5.2 管理接口

RegisterCluster、CreatePool、AdoptSupplyGroup、PublishProfile用于一次初始化；Get/List供查询。Adopt只核对既有安装，不写ConfigMap、不重启组件。发布必须满足组内F一致、型号匹配、规格整除、真实名额配置与验证证据。

AdminGetCapacity使用AdminRead，不要求假租户。现有Gov平台用户tenant_id=0是其认证表示，本方案不重写该模型；Gov验证平台权限后，向GPU服务映射显式AdminRead，不把0当资源租户UUID传递。

SetAdmission只停止新的Resolve，原已接受请求仍使用冻结plan；不声称取消已有调度。在线维护写能力不提供。

### 5.2.1 初装标签和唯一写入方

Adopt核对已有插件配置并生成CLOSED状态的group_id；运维在业务开放前通过现有安装流程，把该group_id、model_key和baseline_id写入对应Node的受管标签。GPU服务不在本次任务中增加Node配置writer，但PublishProfile/OPEN必须实际读取并核对这些标签、Node UID与组成员一致。仅在数据库登记了节点，而Node标签未生效时不能开放规格。给用户容器或业务请求的权限不得包含修改这些节点标签。

这是一轮明确的初始化交接：登记静态组 → 运维设置该组受管标签 → 核对与真实消费验证 → 发布/OPEN。不是每次创建时修改标签，也不是两个writer并发维护同一配置。实际plugin/scheduler安装流程继续由现有运维负责。

### 5.3 租户查询与预检

List/GetProfiles限定授权范围；Resolve参数包括cluster/pool/profile/version/replicas/devices_per_replica/container_name。设备数量首期=1，replicas<=当前owner上限；不允许GPU init/sidecar或额外GPU容器绕过计数。

GetCapacity只读估计。CheckGpuFit可给出容量不足/未知/形态不支持。**合法规格+权限+额度通过、当前容量不足可以提交等待；GPU fit=0不是表单提交上限。**配置未验证、请求形态不受支持、组关闭或额度不足分别拒绝。

客户侧不见其他租户、设备UUID、节点名和原始上报；Binding列表只展示自己已核验的归属。管理员设备详情通过独立接口读取。

### 5.4 GPU使用关联同步接口

`SyncGpuUsage`只接受Governance精确mTLS身份，`ref.owner_service`仍为ani-inference，不要求等于调用者。验证Gov委托来源与受支持owner、原创建、规格摘要和结构；不会查实时GPU空闲决定是否接纳。

每资源只有两种逻辑版本：1=DECLARED，2=ENDED；revision是读投影版本，不是worker租约或执行fencing。两种消息均携带同一不可变ref和GPU计划摘要。ENDED带`GOVERNANCE_CANCELED_UNSENT`或`OWNER_RESOURCE_RELEASED`及事实引用；缺少依据拒绝。

同资源同revision同摘要重放幂等，异内容拒绝；2先到可以直接建立终态，后来的1只允许相同不可变计划且不回退；不得让同resource用新create_operation复活。关系结束不删除真实Binding、不执行QuotaRelease。

### 5.5 ObserveRelease不依赖投影

直接调用者只能是该资源受支持owner；输入可信GpuUsageRef、全部PodRef和关闭操作引用，不要求GPU关联表先存在。查询只返回事实证据，不推进资源关闭，不发退款。

未发出任何外部创建时，owner自己的关闭记录可证明“不曾分配且不再创建”，不调用假GPU释放。曾发出但结果未知时，空Pod列表不能证明无资源；owner必须查清全部可能的副作用。

## 6. 最新Governance上的具体接法

### 6.1 两个正式目录项

`gpu.physical.count / gpu / CONCURRENT`与`gpu.shared_memory_mib / MiB / CONCURRENT`。使用新增版本数据脚本，不修改001实验目录数据脚本，不用启动播种。旧gpu.count继续LAB_ONLY。

新enum`ENFORCED`仅表达额度执行已接线，不表示GPU有空闲或硬件通过全部验收。注册表+显式启用配置派生状态；已装配但当前下游故障时不修改账本或静默取消强制检查。错误和可用性单独表达。

共享向量`replicas × devices_per_replica × profile.shared_memory_mib`，整卡向量`replicas × devices_per_replica`。共享不另扣物理卡，整卡不扣共享MiB。安全int64整数，去重quota_code，乘加溢出拒绝。

### 6.2 原始输入与冻结计划

新增正式`GpuInferenceCreateCanonicalV1`，仍显式schema_version=1，并用`request_kind=inference.gpu.create.v1`区分实验。保存经过实际Inference合同验证的业务参数、GPU原请求、完整冻结plan、gpu-metering-v1。不得将密码、Bearer、任意凭据、未验证GPU字段放进canonical。

request_hash基于可信tenant/actor/owner/action和规范业务输入，**不含解析时间、resource新UUID、当前容量或新生成plan时间**。new请求在事务外Resolve；受权幂等重放先读原请求，内容一致则复用原计划，不再访问最新目录。并发最终仍由Occupy事务内幂等锁/唯一约束决定，不能仅靠前置查询防重。

原源码把到期检查放在Occupy幂等查询之前。正式入口不能默认这已经符合“历史重放与新受理分离”的需求：按当前权限允许查询原操作；新请求才按当前套餐准入；后台投递使用原记录不再占额。是否允许过期用户访问原操作遵循现有入口权限，不能绕过全局闸门。

### 6.3 Consumer旁路的落地方式：可靠派生，不增加关键链写依赖

**本版根据已上传账本代码选择“可恢复扫描+同步进度”，而不是要求改造Occupy/Release为跨库事务或新增强前置注册。**Gov已有不可变canonical、原操作及charges，足以持久派生关联的目标状态。

新增`sys_gpu_usage_sync`仅存关联投递进度，不存第二份额度和运行状态。后台枚举正式GPU CREATE操作，核对至少有一笔完整合法原charge后派生：

```text
原CREATE=CANCELED_UNSENT → desired_revision=2，reason=GOVERNANCE_CANCELED_UNSENT
全部原charge的released_units=original_units → desired_revision=2，reason=OWNER_RESOURCE_RELEASED
否则 → desired_revision=1
```

不能仅凭DELETE ACKED、receipt到达一部分或Pod结束产生revision2；也不能用“无charge集合的all条件为真”将坏数据结束。

每轮将目标与acked_revision比较，落同步进度并领取；提交领取后调用SyncGpuUsage，回执CAS只更新本次租约和已确认revision。revision2由账本最终状态派生，因此即使占额提交后进程崩溃、未写同步行，恢复扫描仍能补齐。必须定期按稳定operation_id分页核对，不只扫新增时间戳，否则旧operation后来的Release会漏掉。

这是相对上一轮“同事务另写同步意图”的工程收敛：可靠依据已经在Gov同事务账本里，旁路可从其重建；创建/退额无需等待GPU同步。已有operation仍是唯一业务投递意图，**不为业务创建再建第二份dispatch表**。

source引用采用可重建的确定性键：受理用`quota-operation:<id>:accepted`，未发撤销用`quota-operation:<id>:canceled-unsent`，最终释放用`quota-operation:<id>:gpu-fully-released`，通过该键可查原charge及相关receipt。单次receipt不必囊括全部charge，但结束前必须核对原向量全量。时间字段只携带原CREATE的持久created_at，不冒充删除完成时间；不得使用每轮扫描时间、最新重试receipt或updated_at生成不同payload。相同ref/revision始终生成同一内容，即使同步进度行重建也一致。同步payload不含账本余额和凭据。

### 6.4 同步状态与业务投递完全分开

原`sys_quota_operations.attempt_count`只统计向Inference发送，不能加上SyncGpuUsage调用；`dispatch_state`仍只有现有投递状态。sync worker失败只更新同步表，永不扣额/退额、永不调用Inference创建。

新请求提交成功但关联延迟：显示“使用关联同步中”；GPU观测到的未关联真实分配仍计容量，等待可信关联后才向租户展示。不让GPU投影成为幂等受理/物理计数的新权威。

### 6.5 正式业务投递

复用QuotaDispatchAdapter注册ani-inference。正式CREATE读取canonical与全量charges，转换为真实Inference方法需要的参数；DELETE携带原create_operation和完整charge快照。业务owner接受完整业务+GPU参数，不能只对GPU摘要ACK。

现有worker只回补第一笔charge，必须修成全量查询并按code排序，失败不调用下游。`QuotaDispatchCommand`增量保存结构化actor字段，不能为统一格式破坏实验adapter。

正式owner接受ACK必须核对operation_id/resource_id/accepted=true；下游业务失败但已接受时仍返回持久接受，失败状态留owner，Gov不按错误字符串退款。

### 6.6 删除和未发撤销的决定

正式DELETE入口先校验当前用户/管理员权限，按租户、owner、resource定位原创建。在本地事务里统一决定：

- 原创建确认QUEUED且attempt_count=0：沿既有CancelUnsent算法封闭领取并退额；同时持久记录本DELETE幂等受理结果，标`CANCELED_BEFORE_DISPATCH`，不是伪造owner ACK。本版用小型`sys_gpu_delete_acceptances`保存公开DELETE的幂等结果；排队分支指向现有DELETE operation，本地撤销分支不生成假投递对象。该表没有worker或第二份删除任务，不新增通用dispatch枚举。
- 已尝试发送或已接受：持久保存现有DELETE operation，不新建charge，可靠交给owner关闭。
- 并发领取竞争：必须共享原operation锁，不先查询再分两个事务乐观退款。对既有方法做局部transaction helper抽取，复用算法，不复制一套余额实现。

有明确DELETE先到支持：信封带原完整计划/charge摘要，owner按ref保存关闭墓碑，即使没有先收到CREATE；迟到CREATE命中终态不执行。若选择不同顺序合同必须另行评审，不能默默依赖单worker按时间排序。

### 6.7 保留退额服务

`quota.service.v1.QuotaReleaseService/ReportQuotaRelease`不变。共享items.released_total仍MiB，不是provider块数；原create operation_id，不是DELETE operation_id。重复全量回调无增量。Inference精确SAN加入已注册owner映射，GPU服务不加入该业务charge的退款owner。

首期Inference只在明确DELETE且整实例完全清理后报告所有原GPU charge全量；部分Pod清理、失败、退出、重启不报告。Gov不跟踪模型Loading/Ready，不用Kubernetes查询判断退款。

### 6.8 API与模块登记

保留已存在`/admin/v1/quota-definitions`、`/admin/v1/tenants/{id}/quota-accounts`及套餐CRUD。新增建议路径见后文。正式Inference路由未在上传Gov中定位，也未取得Inference代码，因此实施前必须完成真实方法/请求/响应/权限映射，不能以文档示意路径假定已实现。

当前module.proto无Inference/GPU枚举。新增业务模块需要显式确认统一编号，同步Proto/Ent enum/数据库检查/API目录/套餐/Casbin，不把实验TENANT默认授权当正式归属。更新`docs/interface-integration-register.md`、定向生成脚本与OpenAPI；保留当前固定Go工具基线，不运行广泛升级或全量Wire。

## 7. Inference执行、删除与证据

### 7.1 创建

受理时验证Gov mTLS、tenant/resource/operation、完整业务摘要、计划摘要、MiB总量与charge向量一致。持久保存业务实例、计划和原charge之后ACK，后台继续创建。无需调用RegisterConsumer。

渲染时按计划的q写vgpu-memory，每副本一份；不能用整个实例的总额写每Pod，也不能临时读取最新factor重新转换。实际replicas与GpuRequest相同，container_name唯一；额外GPU容器/init容器不属于本版。

模型版本、镜像、模型下载/挂载、服务入口沿用实际Inference合同。不同Pod不共享伪造ordinal。创建后必须加载模型并通过真实推理请求，不能以sleep或HTTP存活检查代替。

### 7.2 等待和运行失败

GPU暂满但合法请求受理后Pending，占额不变。容量预检不锁资源。配置不支持、factor未知、参数不合法在受理前拒绝；已接受后遇到基础设施异常留owner阻塞原因，不归成普通“队列满”。不设置首期自动排队退款。

模型失败保留可删除实例；容器普通重启沿既有策略。原资源声明仍存在，因此Gov额度不变化；设备绑定是否变化由实际观测决定，不一概称所有重建保持旧分配。

### 7.3 创建中删除的四种分支

| 阶段 | 处理和退额依据 |
|---|---|
| Gov从未尝试发CREATE | Gov原子撤销+退额，投影是否同步无关 |
| 已尝试发送，owner接受情况未知 | 不本地退款，可靠DELETE给owner；owner处理先到关闭 |
| owner接受但从未发外部创建 | owner封闭本实例后形成未分配关闭事实；不用假ObserveRelease |
| K8s写在途、Pending或运行 | 查清结果、停止继续生成、清理全部相关控制器/Pod/分配，完整完成后报告 |

终态检查必须在实际创建执行控制点成立。单写closed字段不能取消已经通过检查且发出的K8s写入；这类结果未查明就继续持额。首期至少验证“接受后暂缓创建→DELETE→恢复旧执行”普通交错，不把它全部归到未来复杂容灾。

### 7.4 正常释放证据的正向规则

provider adapter必须输出每个实际使用键的`ACTIVE / RELEASE_CONFIRMED / UNKNOWN`，并有当前部署的证据映射表。调度注解只能说明选择；插件成功和运行事实用于确认实际绑定。不能把PodResources返回的伪设备ID或memory块条目直接当硬件UUID。

正常在线节点的释放需要核对工作负载控制器已停止生成、相关Pod/容器已终止、设备分配记录已解除，以及owner没有未知在途创建。具体查询采用现有采集/插件/Kubelet/运行时可用接口，必须填入真实路径；本包不捏造上游存在一个统一ReleaseConfirmed API。[W7]

对同一使用关系，可信解除证据到达后，将其覆盖范围内的旧scheduler选择/旧插件分配退出有效集合。只保留旧true而不退休会永久占容量；随便任一false覆盖全部也不正确。

未知节点/读取失败/单次缺项不表示释放。强删API对象不证明节点进程已停止。[W8] 永久失联自动恢复不作为首期实现，但不能因此自动退额。

### 7.5 两个结束互不代替

GpuUsageProjection.ENDED只是Gov申请结束投影；Binding.RELEASE_CONFIRMED是实际使用解除事实。投影结束不得清Binding；Binding消失不得自动结束业务申请或退额。投影关闭而仍观察到残留访问时，保留占用并报告一致性问题。

完整删除事实和待发ReportQuotaRelease在Inference自身本地事务内持久化，响应丢失继续发同event_id；不同DELETE key关联同一实例结束事实，不重复累计。没有原创建记录而DELETE先到时，使用Gov可信原charge快照，保留对应create墓碑。

## 8. 容量读模型：固定规格下的算法

### 8.1 不建设库存交易系统

物理设备清单、名义供给、已知分配、容量估计都保留；没有LockInventory/CommitInventory/ReturnInventory。GPU服务不能在查询时改变设备分配，也不先挑一张父卡写占用后要求Volcano使用它。

### 8.2 单位归一化与去重

先按`cluster+device`划分证据，再按`pod_uid+container`归并；同使用的多来源只占一份。原始source值注明BLOCKS/MIB/BYTES和来源F；归一化后存memory_mib用于容量计算。不同来源归一化后矛盾则该设备结果未知，不取最小量，也不使其他设备查询全部失败。

不同物理节点上相同索引不是同设备。未放置请求不平均分摊到父GPU；使用关联还没同步不丢实际占用。未纳管工作负载同样减少物理容量。

### 8.3 计算

已验证每卡安全预算`B_d <= R_d × F`，固定规格`m % F=0`，实际最大份数K，已去重有效或未能排除的占用集合C：

```text
used_units_d = |C|
committed_mib_d = sum(claim.memory_mib)
nominal_units_d = min(K, floor(B_d/m), 验证过的计算预算上限)
free_units_d = min(K-used_units_d,
                   floor((B_d-committed_mib_d)/m),
                   验证过的剩余计算预算上限)
```

先检查负数/超预算/模式冲突等不变量，再计算，不用max(0,...)掩盖错误。计算比例仅在后端基线证明可按此硬预算相加时参与；否则需按固定满额运行测试形成保守K，不宣传固定吞吐比例。

首期用真实`devicesplitcount`兑现安全份数。B只能装3份就实际配置K=3，不是页面减成3、底层仍允许4。factor造成量化预算缩小后也重新核对这一点。

整卡组每父卡名义1、存在任何占用冲突则free0；共享与整卡物理集合不重叠，可并列统计，不把两者相加成物理总数。

### 8.4 未知、过期和冲突

故障设备保留绑定，暂停贡献已知free。汇总返回`known_free_units`和`complete=false`及原因；数字0+未知不能显示“全池耗尽”。只读估计未知本身不成为新增请求硬拒绝；实际供给配置不可验证则停止新解析。

错误`CAPACITY_INVARIANT_VIOLATION`表示读模型保守排除冲突设备和停止相关新解析，不宣称自动阻止了所有在途/存量Pending分配。需要真实隔离时走运维流程。

### 8.5 运行指标与配额不同

显存实际用了1GiB但申请6GiB，Gov仍占6144MiB，物理供给仍按6GiB承诺。Node allocatable、实时空闲、已占额度和预计可新增副本分别展示。新请求主流程不依赖精确free数。

## 9. 完整例子

### 9.1 factor与共享申请、整卡并存

假设整卡组W0/W1各1张；共享组S0/S1各物理24576MiB，F=1024，上报24块，每份m=6144MiB/q=6/cores25，K=4，所有组合已经实测。

S0已有2份、S1已有1份；W0已有整卡消费者、W1空闲：

| 项目 | 结果 |
|---|---:|
| 物理GPU | 4张 |
| 整卡名义/可用 | 2/1张 |
| 共享名义/已用/参考可用 | 8/3/5份 |
| 共享已承诺 | 18GiB |
| 共享参考可新增容量 | 30GiB |

租户上限36GiB、已占12GiB，申请两副本，每副本一张6GiB：Gov占12288MiB，使账户到24GiB；**每个Pod写memory=6，两个Pod不是写12，也不是6144。**实际落在哪张卡由调度器决定；整卡组容量不会因为共享申请而改变。

### 9.2 上报错误的对照

同上F=1024，却误写memory=6144：调度器会按6144块理解，远大于单卡24块；通常无法放置，不能把它当普通“资源都被别人用完”。若数量被允许进入实际分配，插件的乘F语义也不是6GiB，说明合同本身错误。

反过来，平台读Node上报24并显示“24MiB”会低估1024倍；把真实bytes指标也再乘F会高估1024倍。测试必须覆盖三个方向，不能仅核对页面单位文本。

### 9.3 因量化和安全预算只能卖三份

物理23552MiB，F=1024 → 23块 →23552MiB；规格6块=6144MiB。floor(23/6)=3，所以K<=3；尾部5120MiB不够一份，不是第四张逻辑卡。其他节点剩余不能拼给这个单设备请求。

若F=10且规格6144，首期直接在发布时拒绝，不进入“算3份或4份”的阶段。要开放需选择可表达的固定规格/F组合并重新实测。

### 9.4 无空闲但有额度

共享8份都满，B租户额度24GiB、已占0，申请2份：Gov占12GiB并受理，Pod等待；consumer同步可能还未到达。物理仍只分配8份，不是实际超卖10份。两份释放后调度，Gov仍12GiB，不第二次扣。

### 9.5 删除与旁路失败

新实例原charge12288MiB；一个Pod退出/重启不退额，DELETE后只清理一个Pod也不退额。两者完全清理，owner报告released_total12288，Gov只退一次。GPU关联结束投影暂时失败，不阻断已完成的退款；设备容量根据解除事实恢复，不等投影结束。

Sync revision2先到、旧revision1后到，GPU侧维持ENDED。真实Binding先于projection存在，记入未关联占用并等待归属核验，不丢弃。

### 9.6 创建中删除

Gov已占额且projection已同步，但CREATE.attempt_count=0：可以本地安全撤销，随后projection变ENDED，不要求Inference伪造删除完成。

CREATE已尝试、ACK丢失：Gov不能因GetResource暂时NotFound退款。DELETE携带原身份/charge给owner；关闭墓碑使迟到CREATE不能新建；已发外部请求查清并清理。未知继续持额，不能靠TTL补偿。

## 11. 数据库与持久化

### 11.1 GPU自有库

本包SQL分为设施、投影和观测：clusters/pools/supply_groups/group_nodes/profiles；gpu_usages；devices/bindings/release_observations。供给配置强约束，容量可由配置与有效分配重建；无inventory_available可手工修改余额。

Binding先保存实际身份、原始引用和单位归一化信息；`verified_usage_ref`可空。后续已验证关联采用同tenant/resource/create匹配，原始未验证标签另存白名单，不靠缺省0租户填充。ENDED不级联删除Binding；从实际分配筛选后再left join投影。

### 11.2 Governance增量

`sys_gpu_usage_sync`一行对应一份正式GPU原创建操作，FK只在Gov本库关联，字段包括desired_revision、acked_revision、payload_digest、租约、下次同步、错误摘要。没有occupied/reserved/running字段；不把它当通用quota项目必须依赖的Consumer表。

原canonical保存完整计划和业务输入。关联任务可以从该持久源重建；不跨库FK、不让GPU服务读Gov数据库。原账本仍满足`occupied=sum(original-released)`。

`sys_gpu_delete_acceptances`保存公开删除受理结果与幂等键：本地撤销或关联既有DELETE operation。没有第二套执行状态或投递worker，不写假owner ACK。具体Ent schema、导出器、Atlas新迁移顺序要按上传仓库工具生成，SQL提案不是已执行迁移。

### 11.3 事务和恢复边界

占额/退额和业务投递源继续现有本地事务；GPU同步在事务外且独立重试。owner接受/关闭/完成事实/通知在owner自身事务。真实K8s操作无法加入PG事务，用稳定身份、执行关闭和结果核对解决，不声称跨服务恰好一次。

关联sync终态保留，历史操作/charge不会为了页面清理硬删除。进程重启恢复已提交事实；当前只读信息不能覆盖实际副作用的不确定性。

## 12. 错误与幂等

保留原Quota错误。新增GPU稳定reason：`MEMORY_UNIT_UNVERIFIED`、`MEMORY_GRANULARITY_MISMATCH`、`FACTOR_MISMATCH`、`CONFIG_DRIFT`、`PROFILE_NOT_ACTIVE`、`SHAPE_UNSUPPORTED`、`USAGE_PROJECTION_CONFLICT`、`BINDING_EVIDENCE_CONFLICT`、`SOURCE_UNKNOWN`。

发布/Resolve中的单位不明、漂移、形态不支持是FailedPrecondition或InvalidArgument；capacity读中未知/不足是结构化结果，不一般返回资源分配失败。已经受理后错误不回滚成“未发生”。

同步同ref/revision异payload冲突保持现场，暂停该条自动覆盖但不操作资源/额度；网络失败重试原数据。投影revision和投递lease_generation不是同一字段。

## 4. 预检响应字段

| 字段 | 类型 | 含义 |
|---|---|---|
| requestedQuotaItems | array{quotaCode:string,units:string} | 服务端对本次请求计算的MiB或整卡数量，仅提示 |
| quotaChecks | array{quotaCode:string,result:string,limit:string,occupied:string,requested:string} | 使用已有当前租户账户；正式提交事务内再验 |
| gpuFit | GpuFit脱敏 | 当前GPU条件，不包括CPU、网络和存储自动通过 |
| additionalReplicasByQuota | string整数 | 仅额度限制下可新增副本数；不含已有预留消费 |
| capacityReferenceReplicas | string整数 | GPU读模型参考数量，不是提交数量上限 |
| capacityReferenceKnown | bool | false不得将0显示为全池耗尽 |

不需要把factor下发给前端供用户修改；后台细节面向管理员诊断即可。

## 5. 正式创建与删除的接线检查

Gov保留原公开Inference业务字段，在原请求上加入gpu。容器名、副本数不能存在两份互相矛盾的来源；如果已有业务字段则服务端只派生一份GpuRequest，或明确拒绝不一致。

创建的GPU附件见`GpuOwnerCreateAttachment`。同步只是旁路，不改变业务接受ACK；Gov仅记录ACKED，查询业务状态继续转真实owner。

正式删除公开结果采用`GpuDeleteAcceptance`建议：deleteOperationId/resourceId/result/dispatchOperationId。result为CANCELED_BEFORE_DISPATCH时没有owner执行，不填假ACK；QUEUED_FOR_OWNER只表示接受，不能即刻显示删除完成。不同DELETE key仍指向同一实例的最终删除事实，owner不重复退额。

管理员代租户清理需显式权限、明确目标tenant、审计原创建关联，仍走同一个删除受理函数。原用户过期不产生强制减账后门。

## 关键结论

factor把上报条目聚合为较大的显存单位，并在容器限制设置时换回MiB尺度。因此必须同时适配供给读取、请求渲染和绑定解释。只乘回Node显示、Pod仍填MiB，是不完整的修复。

本版采用三条设计规则（不是上游强制的产品规则）：规格必须精确整除F；同一静态供给组固定同一F；Governance永远按平台MiB记共享额度。它们让单位差异限制在provider适配，不传播成套餐计量改变。

在核查路径上，6GiB=6144MiB，F=1024时Pod memory填6；节点报24块表示量化后的24576MiB预算，不能当24张卡或24MiB。原始bytes指标不再乘factor。安全预算及slot上限另验，F不是超配。

## 不作的推定

本报告不推定用户目前F为1、10或1024；不推定ConfigMap值必然已生效；不引用某个FAQ数字作为所有Kubernetes扩展资源的上限；不保证提高F就解决任何上报为0问题；不宣称当前tag与用户部署相同。实际错误日志可能还涉及配置未加载、插件异常或其他集成问题。

本包未复制上游完整源文件；以上链接可用于复核来源，关键公式来自上述版本代码，运行可用性仍需真实环境验收。
